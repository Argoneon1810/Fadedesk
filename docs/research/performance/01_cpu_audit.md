# 확장의 CPU 부담 측정 (2026-11-17, 1.2.0)

## 왜 쟀나

사용자 관찰: YouTube 두 개를 틀면 CPU(기기 전체)가 탭마다 10% 넘게 오른다. 이게 확장 때문인지, 줄일 수 있는지,
기능을 위해 감수해야 하는지를 가르려고 쟀다.

## 어떻게 쟀나

- 도구: `scripts/measure-audio-cpu.mjs` (개발용, 배포물에 안 들어감). 새 프로필 Chrome(헤드리스, `--mute-audio`)을 CDP 파이프로
  띄우고 `Extensions.loadUnpacked`로 `dist/unpacked`를 올린 뒤, 로컬 `<audio>` 반복 재생 페이지를 탭 2개에 튼다. **영상은 없다** — 영상 디코딩 몫을 빼고 확장 몫만 보려는 설계.
- 주 지표: `SystemInfo.getProcessInfo`의 renderer + GPU + AudioService 프로세스 CPU 시간 증가량. 브라우저·네트워크
  프로세스는 새 프로필의 자체 작업(구성 요소 갱신 등)으로 회차마다 크게 흔들려 주 지표에서 뺐다(확장 메시지는 초당 1회 미만).
- 유효성 관문: 재생 시각이 흐르는가, 확장 오디오 회로가 `running`인가, 0.075초 계산이 실제 주기(약 13회/초)로 도는가. 하나라도 어긋나면 INVALID로 버린다(12회 중 2회 — 헤드리스 자동 재생이 가끔 시작 안 됨).
- 시나리오를 번갈아 3회. 차이가 회차 간 흔들림보다 작으면 "잴 수 없음"으로 본다.
- GPU: 헤드리스에서도 실제 GPU(RTX 4060 Laptop)로 합성·래스터가 켜져 있었다(`SystemInfo.getInfo`). 소프트웨어 렌더링으로 부풀은 값이 아니다.

## 결과 (탭 2개, 논리 코어 16개 기기)

| 상황 | 코어 1개 기준 | 기기 전체 | 확장 없음 대비 |
|---|---|---|---|
| 확장 없음 | 14.2% | 0.89% | — |
| 확장 켬, 팝업 닫힘 | 22.4% | 1.40% | +0.5% |
| 확장 켬, 노멀라이저 끔 | 21.5% | 1.35% | +0.46% |
| 확장 켬, 팝업 열림 | 55.5% | 3.47% | +2.6% |

- 오디오 처리 회로(WebAudio): 문맥마다 Render Capacity 약 3.3%(코어 1개 기준). 팝업 닫힌 상태의 확장 몫 거의 전부.
- 노멀라이저 0.075초 계산(FFT 포함): 켬과 끔의 차이 +0.9%(코어 1개) — 잡음 폭(1.8%) 안. **고칠 가치 없음.**
- 팝업 열림: renderer +13%, GPU 프로세스 +18~20%(코어 1개 기준). 팝업 기본 스레드는 초당 약 49ms 일하고 그중 배치(layout)가
  19.5ms(초당 12.6회 = VU 갱신마다 1회, 회당 약 1.5ms), 스크립트 4.2ms, 스타일 1.6ms.

## 결론

1. **오디오 렌더링은 문제가 아니다.** 팝업을 닫으면 확장 몫은 탭당 기기 전체 약 0.25%. 사용자가 본 탭당 10%는 영상 재생 몫이다.
2. **팝업 그리기가 확장 몫의 대부분이다.** 팝업(또는 팝아웃 창)을 열어 두는 동안 기기 전체 약 +2%.
3. 원인 후보(코드 판독): VU 갱신(80ms)마다 채널 보조 글자·트림 배지 등을 값이 같아도 `textContent`로 다시 써서 매번 문서 전체
   배치가 일어남. LED 칸 40개/채널의 `backgroundColor`·`opacity`를 매번 다시 써서 다시 그리기·래스터가 일어남.

## 팝업 그리기 최적화 (같은 날, 탭 2개, 코어 1개 기준 "팝업 열림 − 닫힘")

| 단계 | 팝업 몫 | 기기 전체 | GPU 프로세스 | 팝업 배치(layout) |
|---|---|---|---|---|
| 수정 전 | +33.1% | +2.07% | 18~20% | 12.6회/초, 19.5ms/초 |
| 1. 같은 값이면 쓰지 않기 (`src/popup/dom-write.ts`) | +22.1% | +1.38% | 14.0% | 2.0회/초, 2.6ms/초 |
| 2. VU LED를 transform으로만 움직이기 | +13.2% | +0.83% | 4.9% | 2.1회/초, 4.3ms/초 |

- 1단계: 채널 보조 글자·트림 배지·LED 색을 값이 같으면 다시 쓰지 않는다. 같은 글자를 `textContent`로 다시 넣는 것만으로 매 프레임 문서 배치가 일어나고 있었다.
- 2단계: 꺼진 칸 20개는 한 번만 그리고, 켜진 칸을 칠해 둔 층을 창 안에서 `translateY`로 밀고(창과 안쪽 층을 반대로 밀어 칸 자리 고정), 정점 칸도 `translateY`·`opacity`로만 움직인다. 다시 그리기·래스터가 사라져 GPU 프로세스가 14%→4.9%. 칸 색은 CSS 변수(`--c-success`·`--c-warning`·`--c-danger`)라 테마 바꿈도 JS 없이 따른다. 수정 전·후 화면 캡처 비교에서 LED 모양 같음.
- 남은 것: 팝업 스타일 계산이 1.4→6~7ms/초로 늘었다(transform 문자열에 `calc(var())`를 매번 넣음). 열 높이를 기억해 px로 넣으면 줄일 수 있으나 남은 몫이 작아 미뤘다.

## 뒤집은 추정

- 측정 전에는 "노멀라이저 계산·FFT를 팝업 닫힘 때 쉬게 하기"를 줄일 곳으로 꼽았다. 측정으로 효과가 잡음 이하임이 드러나 뺐다.
- "헤드리스라 GPU가 소프트웨어로 돌아 팝업 몫이 부풀었을 수 있다"고 봤으나, GPU 정보 확인 결과 실제 GPU로 돌았다.

## 다시 재는 법

```sh
npm run build
node scripts/measure-audio-cpu.mjs                      # 3회 × off,on,popup,nonorm (약 7분)
node scripts/measure-audio-cpu.mjs --scenarios on,popup # 팝업 몫만
node scripts/measure-audio-cpu.mjs --url <주소> --headed # 실제 사이트 (동의 화면·광고로 흔들림)
```
